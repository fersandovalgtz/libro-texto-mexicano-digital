# LTMD-U1 FTRL completion ledger 0.1

## Purpose

This ledger is the machine-readable control surface for the exhaustive LTMD-U1 denominator of 542 documentary identities. It does not replace source manifests, processing inventories, run manifests, or the retained-source register; it joins their operational state into one auditable row per historical viewer identity.

The ledger is metadata-only and contains no OCR text, snippets, or semantic claims.

## Canonical distinctions

The ledger preserves the following non-equivalences:

- `corpus_ready != semantic_ready`
- `ocr_available != text_verified`
- `search_hit != historical_claim`
- `zero_hits != demonstrated_absence`
- `computationally_validated != archival_complete`

A wave can therefore be technically validated while remaining semantically unverified or archivally incomplete.

## Documentary denominator

The source of truth for identity membership and operational domain is `data/catalog/ltmd_u1_coverage.csv`. The generator requires exactly 542 unique `viewer_key` values and the following domain-derived wave denominators:

Waves are logistical partitions only. They never reduce the 542-identity denominator.

## Documentary dispositions

Exactly three documentary dispositions are permitted:

1. `required_ftrl_processing`
2. `active_retention`
3. `final_exception`

`active_retention` blocks global FTRL-U1 closure. `final_exception` remains inside the denominator and must never receive fabricated source or OCR content.

## Processing topology

Where a wave has a versioned FTRL processing inventory, the ledger records the canonical processing object and relation type. Historical aliases remain separate documentary rows. Source-page totals are counted on canonical processing objects only to avoid double counting aliases.

## Wave state

`data/research/ltmd_u1_ftrl_wave_state.json` is a compact public registry of verified operational state. It may contain GitHub run IDs, commit SHAs, and logical Drive destinations, but never private Drive IDs, URLs, credentials, OCR text, snippets, or private-key material.

State transitions must be evidence-backed:

- `pending -> in_progress` only after an identified run exists;
- `in_progress -> validated` only after the complete technical gates pass;
- `preservation_in_progress -> archival_complete` only after the encrypted/private copy is physically present in the canonical private Drive destination and its integrity evidence has been checked.

## Generated files

- `data/research/ltmd_u1_ftrl_completion_ledger.csv`
- `data/research/ltmd_u1_ftrl_completion_summary.json`

Both are reproducibly generated by `scripts/build_ltmd_u1_ftrl_completion_ledger.py`.

## Current interpretation

The ledger is a technical and archival progress instrument. It must not be cited as evidence that OCR text has been human-verified, that a search result establishes a historical proposition, or that a zero-hit query demonstrates historical absence.
